      Start here

      How to use this book

      Each chapter follows the same shape: what the effect is, how it works underneath, where it lives in your portfolio, and a small piece of code you can copy into another project.

      Two habits will help more than anything else. First, play with every demo before reading the code, so you know what you are trying to explain. Second, change one number at a time in your own project and watch what happens. Animation is a feel skill. You build it by adjusting a duration from 300ms to 900ms and seeing why one looks cheap and the other looks expensive.

      The code uses plain CSS and plain JavaScript wherever possible. The React versions are shown where your portfolio uses them, and they are only a thin wrapper around the same ideas.

      Your portfolio at a glance

      Everything you see move in it comes from just six techniques: transitions (hover), keyframes (the hero), IntersectionObserver (fade in on scroll), scroll math (parallax and the word-by-word text), requestAnimationFrame (the counting numbers), and a few layout tricks (the menu, the responsive stats). Chapters 2 to 9 take them one at a time.

      Chapter 1

      How the browser draws a frame

      Before any code: the one idea that decides whether an animation feels smooth or janky.

      Every time something on screen changes, the browser goes through up to four steps:

      The rendering pipeline
      Stylewhich CSS applies
      Layoutsizes and positions
      Paintdraw the pixels
      Compositestack the layers
      width, height, top, left, margin, font-size: all four steps, every frame. Expensive.
      color, background, box-shadow: skips layout, but repaints. Medium.
      transform, opacity: composite only, often on the GPU. Cheap and smooth.

      When you animate left: 0 to left: 200px, the browser has to recalculate the position of the element (and possibly its neighbors), repaint it, then composite, 60 times a second. When you animate transform: translateX(200px), the element has already been painted. The browser just slides the finished picture around.

      The golden rule

      Animate transform and opacity. Almost every motion you want can be built from them: translate moves, scale grows, rotate turns, opacity fades.

      In your portfolio: the hero text slide, the scroll fade-ins, the hover zoom, the hamburger icon and the menu links all use only transform and opacity. The one exception is the underline on your email link, which animates background-size. It is tiny, so it is fine.

      Chapter 2

      Design tokens with CSS variables

      One place to define colors, timing and spacing. Change it once, the whole site follows.

      A CSS custom property (a "variable") starts with two dashes and is read with var(). Declare them on :root and every element can use them.

      src/styles/tokens.css
      :root {
  --bg: #fbfbfd;
  --text: #1d1d1f;
  --muted: #6e6e73;
  --accent: #0066cc;
  --ease: cubic-bezier(0.16, 1, 0.3, 1);   /* the "Apple" curve */
}

.card {
  background: var(--bg);
  color: var(--text);
  transition: transform 0.6s var(--ease);
}

      Dark mode for free

      Because every color is a variable, dark mode is just redefining the same names inside a media query. No component CSS changes.

      @media (prefers-color-scheme: dark) {
  :root {
    --bg: #000000;
    --text: #f5f5f7;
    --muted: #a1a1a6;
    --accent: #2997ff;
  }
}

      Variables as inputs to animation

      This is the part most people miss: variables can carry per-element values into your CSS. You set a variable inline in JSX or HTML, and the stylesheet does the math.

      <!-- HTML / JSX: each element gets its own index -->
<li style="--i: 0">Work</li>
<li style="--i: 1">About</li>
<li style="--i: 2">Skills</li>

/* CSS: delay grows with the index (a "stagger") */
li { transition-delay: calc(var(--i) * 60ms + 80ms); }

      Three elements, one CSS rule, three different delays. You will see this pattern in chapters 4, 5 and 10.

      In your portfolio: src/styles/tokens.css holds all colors and the --ease curve. --i (stagger) and --d (delay) are set inline by the Hero, Reveal and Nav components.

      Chapter 3

      Transitions: smooth hover and state changes

      A transition says: "when this property changes, don't jump, glide."

      .btn {
  transform: scale(1);
  transition: transform 0.35s var(--ease);
  /*          property  duration  timing   (delay optional) */
}
.btn:hover { transform: scale(1.06); }

      You declare the transition on the base state, not on :hover. That way it also animates on the way back. The browser compares the start and end values and fills in the frames between.

      Live demo · hover or tap the button

      Duration: how long?

      • 150 to 250ms: small feedback like color or a tap press.
      • 300 to 500ms: hover lifts and buttons.
      • 600 to 1200ms: big entrances like your scroll reveals. Larger movement needs more time to feel natural.

      Easing: the part that makes it feel "Apple"

      Easing is the shape of the speed over time. linear moves at constant speed, which feels robotic because nothing in the real world does that. cubic-bezier(x1, y1, x2, y2) lets you draw the curve with two control points.

      The curve in your portfolio, cubic-bezier(0.16, 1, 0.3, 1), is an "ease-out" with a strong start: it covers most of the distance almost instantly, then spends a long time settling. Press play and compare:

      Live demo · same distance, same time, different easing

      ease
      ease-in-out
      (0.16, 1, 0.3, 1)
      Watch the last one: fast start, long gentle landing.

      Rule of thumb: things entering the screen use ease-out (fast then slow). Things leaving use ease-in. Things moving between two places on screen use ease-in-out. When in doubt, use your --ease variable.

      Pitfalls

      Avoid transition: all. It animates things you didn't intend (including layout properties) and hides bugs. List the properties you mean.

      Transitions can't animate display. display: none to block is a jump. Use opacity plus visibility instead (chapter 10 shows exactly how).

      Hover doesn't exist on phones. A tap makes :hover stick. Wrap hover effects in @media (hover: hover) so they only run where a real pointer exists.

      In your portfolio: buttons (Button.css), the arrow nudge (ArrowLink.css), tags, nav links and the screenshot zoom (Media.css) are all transitions.

      Chapter 4

      Keyframes: animations that run on their own

      Transitions need a trigger (hover, a class change). Keyframes just run, which makes them right for page load.

      @keyframes rise {
  from { transform: translateY(100%); }
  to   { transform: translateY(0); }
}

.title {
  animation: rise 1.1s var(--ease) 0.2s forwards;
  /*         name  duration timing  delay  fill-mode */
}

      The shorthand is animation: name duration timing-function delay iteration-count direction fill-mode. The one that trips everyone up is fill-mode:

      • forwards: after the animation ends, keep the final keyframe. Without it, the element snaps back to its starting style.
      • backwards: during the delay, apply the first keyframe. Without it, the element shows its normal style until the delay finishes, then jumps.
      • both: does both.

      The text "mask" reveal from your hero

      The headline doesn't fade in. Each line slides up from behind an invisible edge. The trick has two layers:

      1. An outer .line with overflow: hidden. This is the mask. Anything outside its box is invisible.
      2. An inner .line-in pushed down with translateY(112%), so it starts fully below the mask, then animated to 0.

      The text appears to rise out of nothing. Toggle overflow: hidden off to see what's really happening:

      Live demo · the hero headline effect
      I build web apps, front to back.
      Hero.css
      .line { display: block; overflow: hidden; padding-bottom: 0.1em; margin-bottom: -0.1em; }

.line-in {
  display: block;
  transform: translateY(112%);
  animation: hero-rise 1.2s var(--ease) forwards;
  animation-delay: calc(0.18s + var(--i) * 0.13s);   /* stagger */
}

@keyframes hero-rise { to { transform: translateY(0); } }
      Details worth knowing

      Only a to keyframe? That's allowed. The missing from uses the element's current style, which here is the translateY(112%) already set in the CSS.

      Why the padding and negative margin? overflow: hidden clips to the line box, which cuts off the tails of letters like g and y. padding-bottom: 0.1em gives them room, and margin-bottom: -0.1em cancels the extra space so the lines still sit tight.

      Stagger: the inline --i variable (0, 1) feeds calc() in the delay, so the second line starts 0.13s after the first.

      In your portfolio: Hero.css (headline, subtitle and buttons fade in with growing delays). The same fade is used on the eyebrow text.

      Chapter 5

      Scroll reveal with IntersectionObserver

      Elements fade up as they enter the screen. This is the single most-used scroll effect on the web.

      You need two things: CSS that defines the hidden and visible states, and JavaScript that notices when an element enters the viewport and flips a class.

      CSS
      .reveal {
  opacity: 0;
  transform: translateY(30px);
  transition: opacity 1s var(--ease), transform 1s var(--ease);
  transition-delay: var(--d, 0ms);
}
.reveal.in { opacity: 1; transform: none; }
      JavaScript (vanilla)
      const io = new IntersectionObserver((entries) => {
  entries.forEach((entry) => {
    if (entry.isIntersecting) {
      entry.target.classList.add('in');
      io.unobserve(entry.target);          // animate once, then stop watching
    }
  });
}, { threshold: 0.12, rootMargin: '0px 0px -6% 0px' });

document.querySelectorAll('.reveal').forEach((el) => io.observe(el));

      Why not just listen to the scroll event?

      A scroll listener fires dozens of times per second and you'd have to measure every element each time, which is slow. IntersectionObserver lets the browser do the watching and call you only when visibility changes. It is faster and much less code.

      The two options

      • threshold: 0.12: fire when 12% of the element is visible (0 = any pixel, 1 = all of it).
      • rootMargin: '0px 0px -6% 0px': shrinks the watched area from the bottom, so elements trigger slightly after they enter instead of the instant their top edge appears. It makes the reveal visible, not wasted just under the fold.

      The React version

      React doesn't change the idea, it just wraps it so you can reuse it. A hook holds the observer, a component applies the class:

      hooks/useInView.js
      import { useEffect, useRef, useState } from 'react';

export default function useInView() {
  const ref = useRef(null);
  const [seen, setSeen] = useState(false);

  useEffect(() => {
    const el = ref.current;
    if (!el) return;
    const io = new IntersectionObserver(([entry]) => {
      if (entry.isIntersecting) { setSeen(true); io.disconnect(); }
    }, { threshold: 0.12, rootMargin: '0px 0px -6% 0px' });
    io.observe(el);
    return () => io.disconnect();        // cleanup when the component unmounts
  }, []);

  return [ref, seen];
}
      components/ui/Reveal.jsx
      export default function Reveal({ as: Tag = 'div', delay = 0, className = '', children }) {
  const [ref, seen] = useInView();
  return (
    <Tag ref={ref} className={`reveal ${seen ? 'in' : ''} ${className}`}
         style={{ '--d': `${delay}ms` }}>
      {children}
    </Tag>
  );
}

// usage: <Reveal delay={100}><h2>Hello</h2></Reveal>
      Pitfall: hidden forever

      If the JavaScript fails to load, .reveal elements stay at opacity: 0 and the page looks empty. For client projects, add a js class to <html> from a tiny inline script and write the rule as .js .reveal { opacity: 0; ... }, so content is visible without JavaScript.

      In your portfolio: hooks/useInView.js and components/ui/Reveal.jsx. It wraps almost every block on the page.

      Chapter 6

      Scroll-linked animation: effects tied to scroll position

      The reveal in chapter 5 plays once. These effects are scrubbed: scroll a little, they move a little. Scroll back, they reverse.

      Your portfolio has two: the hero fading and drifting as you leave it, and the statement paragraph where words brighten one by one. They share one recipe:

      1. Read where the element is relative to the screen.
      2. Convert that to a progress number from 0 to 1.
      3. Use the progress to set a style (opacity, transform).

      The one formula to memorize

      progress = clamp( (value - start) / (end - start), 0, 1 )

const clamp = (n, min, max) => Math.min(max, Math.max(min, n));

      It maps any range onto 0 to 1. If value is at start, progress is 0. If it's at end, it's 1. The clamp stops it going outside that range. With a progress value you can drive anything: opacity = 1 - progress, translateY = progress * 100, and so on.

      Throttle with requestAnimationFrame

      Scroll events can fire more often than the screen refreshes. Doing work on each one is wasteful. requestAnimationFrame says "run this just before the next paint", and canceling the previous request means you do the work at most once per frame:

      hooks/useScrollFrame.js
      useEffect(() => {
  let raf = 0;
  const run = () => {
    cancelAnimationFrame(raf);
    raf = requestAnimationFrame(() => saved.current());
  };
  saved.current();                                    // run once on mount
  window.addEventListener('scroll', run, { passive: true });
  return () => {
    cancelAnimationFrame(raf);
    window.removeEventListener('scroll', run);
  };
}, []);

      { passive: true } promises the browser you won't call preventDefault(), so it can keep scrolling smooth without waiting for your code.

      Example 1: the hero drift

      const y = Math.min(window.scrollY, window.innerHeight);
const p = y / window.innerHeight;                  // 0 at top, 1 after one screen

el.style.transform = `translate3d(0, ${y * 0.18}px, 0) scale(${1 - p * 0.05})`;
el.style.opacity   = String(Math.max(0, 1 - p * 1.2));

      The text moves down at 18% of the scroll speed (so it seems to lag behind), shrinks by 5% and fades out. That's a "parallax" effect: layers moving at different speeds create depth.

      Example 2: words that light up

      Each word gets an opacity of 0.2 + 0.8 * t, where t is how far the scroll progress has passed that word:

      const progress = clamp((vh * 0.85 - rect.top) / (vh * 0.5 + rect.height), 0, 1);

words.forEach((word, i) => {
  const t = clamp(progress * (n + 2) - i, 0, 1);   // word i starts when progress reaches i/(n+2)
  word.style.opacity = String(0.2 + 0.8 * t);
});

      Multiplying progress by n + 2 spreads the words along the timeline, and subtracting i delays each word a little more than the last. The + 2 gives the last word a bit of room so it finishes lit before the paragraph leaves.

      Write to the DOM directly, not to state

      Notice the code sets el.style.opacity through a ref instead of calling setState. State changes re-render the component 60 times a second, which is wasteful for something purely visual. For per-frame animation, touch the element directly. Reserve state for things that change what renders, like the active nav link.

      The modern, JavaScript-free option

      Newer browsers can do scrubbed animation in pure CSS with scroll-driven animations:

      @keyframes fade-in { from { opacity: 0; transform: translateY(40px); } to { opacity: 1; transform: none; } }

@supports (animation-timeline: view()) {
  .card {
    animation: fade-in linear both;
    animation-timeline: view();            /* progress = how far the element crossed the viewport */
    animation-range: entry 0% cover 30%;   /* start when it enters, finish at 30% covered */
  }
}

      Browser support for this is still catching up, so check caniuse.com for scroll-driven animations before relying on it, and keep the JavaScript version (or no animation) as the fallback inside the @supports guard. The JavaScript approach you used works everywhere today.

      In your portfolio: Hero.jsx (drift), Statement.jsx (words), both built on hooks/useScrollFrame.js.

      Chapter 7

      Counting numbers with requestAnimationFrame

      CSS can't animate the text "0" into "99". For that you drive the animation yourself, one frame at a time.

      requestAnimationFrame(callback) calls you before every screen repaint and hands you a timestamp. You compute how much time has passed, convert it to progress from 0 to 1 (same idea as chapter 6), run it through an easing function, and update the number.

      Vanilla JS
      function countUp(el, to, duration = 1600) {
  let start;
  const easeOutExpo = (p) => (p === 1 ? 1 : 1 - Math.pow(2, -10 * p));

  function tick(now) {
    start = start ?? now;                              // first frame sets the start time
    const p = Math.min((now - start) / duration, 1);   // progress 0..1
    el.textContent = Math.round(to * easeOutExpo(p));
    if (p < 1) requestAnimationFrame(tick);            // keep going until done
  }
  requestAnimationFrame(tick);
}
      Live demo · pick an easing and replay
      0ms

      With linear the number climbs at a steady, mechanical pace. With easeOutExpo it races up and slows into the final value, which feels like it is "landing" and draws the eye to the result.

      Making it start when visible

      In your portfolio the counter doesn't start on page load, it starts when you scroll to it. That's the useInView hook from chapter 5 feeding a seen flag into the effect that runs the loop, and returning cancelAnimationFrame as cleanup so the loop stops if the component disappears.

      Small details that matter

      Jittering digits: proportional fonts make the number wiggle as digits change. Add font-variant-numeric: tabular-nums so every digit has the same width.

      Layout jumps: add white-space: nowrap so "99 ms" never wraps mid-animation.

      Reduced motion: if the user prefers less motion, skip the loop and set the final number immediately (chapter 11).

      In your portfolio: components/ui/CountUp.jsx, used by the stats under each project.

      1. Dim the others

      .items:hover span      { opacity: 0.32; }   /* hovering the group dims all children */
.items span:hover      { opacity: 1; }      /* the hovered child restores itself   */

      Order and specificity do the work here: the second rule is more specific, so it wins for the hovered child. The group rule only applies while the pointer is inside the container.

      2. Zoom inside a frame

      .frame { overflow: hidden; border-radius: 16px; }
.frame img { transition: transform 1.4s var(--ease); }
.frame:hover img { transform: scale(1.04); }

      The frame hides the overflow, so the image grows but the shape stays. Hover the frame, not the image, so the whole card is the target. A long duration with an ease-out curve makes it a slow, premium "breathe".

      3. Growing underline

      .link {
  background: linear-gradient(currentColor, currentColor) 0 100% / 0 2px no-repeat;
  transition: background-size 0.6s var(--ease);
}
.link:hover { background-size: 100% 2px; }

      A one-color gradient is used as a line. Its background-size goes from 0 width to 100%, and 0 100% pins it to the bottom-left. currentColor means it always matches the text color. (This is the underline on your email link.)

      4. Arrow nudge

      .more span { display: inline-block; transition: transform 0.35s var(--ease); }
.more:hover span { transform: translateX(4px); }

      Note display: inline-block. Transforms do nothing on plain inline elements, a common "why won't it move?" bug.

      5. Press feedback

      .btn:hover  { transform: scale(1.04); }
.btn:active { transform: scale(0.97); }   /* shrink slightly while pressed */

      Only on devices that can hover

      @media (hover: hover) {
  .btn:hover { transform: scale(1.04); }
}

      On phones, a tap triggers :hover and it stays "stuck" until you tap elsewhere. Wrapping hover rules in this query avoids that. Keep :active outside it, since that is what gives touch screens their press feedback.

      In your portfolio: Skills.css (dim others), Media.css (zoom), Contact.css (underline), ArrowLink.css (nudge), Button.css (press).

      Chapter 9

      Responsive layout that doesn't break

      Animation looks amateur if the layout around it breaks on a phone. These are the tools used to make your portfolio work from 360px to ultrawide.

      1. Fluid sizes with clamp()

      font-size: clamp(36px, 10vw, 112px);
/*                min   preferred  max          */

      The browser uses 10vw (10% of the viewport width) but never goes below 36px or above 112px. On a 390px phone that's 39px, on a 800px tablet 80px, on a desktop it stops at 112px. One line replaces three media queries.

      2. Grid for columns

      .stats { display: grid; grid-template-columns: repeat(3, 1fr); gap: 24px; }

@media (max-width: 560px) {
  .stats { grid-template-columns: 1fr; }     /* one column on phones */
}

      1fr means "one share of the free space". repeat(3, 1fr) is three equal columns.

      3. Media queries vs container queries

      A media query asks "how wide is the screen?" A container query asks "how wide is the box I'm inside?" That makes a component responsive to where it's placed, not just which device it's on. Drag the slider to resize the box and watch the layout switch, with no change to the screen size:

      Live demo · container query
      10REST API endpoints
      99ms warm response
      15bcrypt salt rounds
      .wrapper { container-type: inline-size; }

@container (max-width: 440px) {
  .stats { grid-template-columns: 1fr; }
}

      Your portfolio uses media queries, which is fine for a page-level layout. Use container queries when you build a component (a card, a stat block) that will be reused in different-width places.

      4. Pick breakpoints where the layout breaks, not by device

      Phones and tablets come in hundreds of sizes. Instead of "iPhone breakpoint", ask "at what width does this look bad?" Your portfolio's breakpoints came from exactly that: the stats cramped at 560px, the About columns got tight at 720px, the nav links ran out of room at 760px.

      5. Mobile browser details

      • Viewport units: 100vh on phones includes the area behind the browser bars, so content gets clipped. Use 100svh (smallest visible height), with 100vh as the fallback line above it.
      • Notches and home bars: add viewport-fit=cover to the viewport meta tag, then pad with env(safe-area-inset-top) and friends so content doesn't hide behind them.
      • Touch targets: keep tappable things about 44px tall. That's why the nav links and arrow links have extra vertical padding.
      • Overflow: long strings (like an email) can push the page wider than the screen. overflow-wrap: anywhere plus a clamp() font size keeps them inside.
      .hero { min-height: 100vh; min-height: 100svh; }      /* later line wins where supported */
.nav  { padding-top: env(safe-area-inset-top, 0px); }
      In your portfolio: the media queries at the bottom of Work.css (stats become rows), About.css, Skills.css and Nav.css. Variables for the safe areas are in tokens.css.

      Chapter 10

      The navigation: blur, hamburger and menu overlay

      Three separate ideas in one component.

      1. The frosted nav bar

      .nav {
  position: fixed; top: 0; left: 0; right: 0;
  background: rgba(251, 251, 253, 0.72);          /* semi-transparent */
  backdrop-filter: saturate(180%) blur(20px);     /* blurs what's behind it */
  border-bottom: 1px solid transparent;
  transition: border-color 0.4s ease;
}
.nav.solid { border-bottom-color: var(--line); }  /* JS adds .solid after scrolling 8px */

      The background must be semi-transparent, or there's nothing to blur. Add -webkit-backdrop-filter alongside for Safari support in older versions.

      2. The hamburger that becomes an X

      Just two thin bars, positioned absolutely. Opening the menu rotates them 45° in opposite directions, nudged toward the center so they cross.

      .burger i { position: absolute; left: 13px; right: 13px; height: 1.5px;
            background: currentColor; transition: transform 0.45s var(--ease); }
.burger i:nth-child(1) { top: 19px; }
.burger i:nth-child(2) { top: 25px; }

.open .burger i:nth-child(1) { transform: translateY(3px)  rotate(45deg); }
.open .burger i:nth-child(2) { transform: translateY(-3px) rotate(-45deg); }

      3. The full-screen menu with staggered links

      Live demo · tap the menu button
      Rhythm
      Work About Skills Contact 
      .menu {
  position: fixed; inset: 0;
  opacity: 0;
  visibility: hidden;
  transition: opacity 0.45s ease, visibility 0s linear 0.45s;   /* hide AFTER the fade-out */
}
.menu.open {

      Why visibility as well as opacity? An element at opacity: 0 is invisible but still clickable and focusable by keyboard. visibility: hidden removes both, but it can't be faded. The trick is the transition on visibility: 0s linear 0.45s means "change instantly, but only after waiting 0.45s", which is after the fade-out finished. On the way in, the rule overrides it so it flips immediately.

      The JavaScript around it

      • Toggle an open class from a button, and keep aria-expanded in sync for screen readers.
      • Lock page scroll while open: document.body.style.overflow = 'hidden', restored on close.
      • Close on Escape, on link click, and if the window grows past the mobile breakpoint.
      The bug that costs everyone an afternoon

      If a parent has backdrop-filter, filter, transform or perspective, it becomes the containing block for any position: fixed children. Your "full-screen" menu then fills only the nav bar. That is why the portfolio renders the menu as a sibling of the header, not a child.

      In your portfolio: components/layout/Nav.jsx and Nav.css.

      Chapter 11

      Performance and accessibility

      The difference between an animation that impresses and one that makes someone's laptop fan spin up or makes them feel unwell.

      Performance checklist

      • Only animate transform and opacity (chapter 1).
      • Use will-change sparingly. will-change: transform tells the browser to promote the element to its own layer ahead of time. Great for the hero that moves on scroll. Put it on dozens of elements and you waste memory. Never apply it to everything.
      • Don't read layout right after writing styles in the same frame. Calling getBoundingClientRect() after changing a style forces the browser to recalculate immediately. Read all values first, then write.
      • Throttle scroll work with requestAnimationFrame and use { passive: true } (chapter 6).
      • Stop watching when done. Disconnect observers after a one-time reveal.

      See it in DevTools

      • Rendering tab (Chrome DevTools, three-dot menu, More tools, Rendering): turn on Paint flashing to see which areas repaint, and Frame Rendering Stats for a live FPS meter.
      • Performance tab: record while you scroll. Long red bars or frames over 16ms show where you're dropping frames.

      Respect reduced motion

      Some people get dizziness or nausea from parallax and large movement. They enable "Reduce motion" in their operating system, and you can detect it:

      @media (prefers-reduced-motion: reduce) {
  html { scroll-behavior: auto; }
  .reveal { opacity: 1; transform: none; transition: none; }
  .line-in { transform: none; animation: none; }
}
      // JavaScript side
export const prefersReducedMotion =
  window.matchMedia('(prefers-reduced-motion: reduce)').matches;

if (prefersReducedMotion) { /* skip parallax, set final values immediately */ }

      This doesn't mean "no animation". It means no large movement. Content should still be fully usable and visible.

      Other accessibility basics

      • Animation should never hide content a user needs. Never make the only way to read something depend on an animation finishing.
      • Menu buttons need aria-label and aria-expanded. Hidden menus should use visibility: hidden so keyboards can't tab into them.
      • Keep keyboard focus visible. Don't remove outlines without replacing them.

      Chapter 13

      Copy-paste recipes

      A toolkit to carry into any project. Each one is complete and independent.

      Fade up on scroll (CSS and vanilla JS)

      .reveal { opacity: 0; transform: translateY(30px);
          transition: opacity 1s cubic-bezier(.16,1,.3,1), transform 1s cubic-bezier(.16,1,.3,1); }
.reveal.in { opacity: 1; transform: none; }

new IntersectionObserver((es, io) => es.forEach(e => {
  if (e.isIntersecting) { e.target.classList.add('in'); io.unobserve(e.target); }
}), { threshold: 0.12 }).observe(el);   // call .observe(el) for each element

      Stagger a group

      .stagger > * { transition-delay: calc(var(--i, 0) * 80ms); }
/* give each child style="--i: 0", "--i: 1", ... */

      Hover lift for cards

      .card { transition: transform 0.5s cubic-bezier(.16,1,.3,1), box-shadow 0.5s ease; }
@media (hover: hover) {
  .card:hover { transform: translateY(-6px); box-shadow: 0 18px 40px rgba(0,0,0,.12); }
}

      Text slide-up on load

      <h1><span class="line"><span class="line-in">Hello world</span></span></h1>

.line { display: block; overflow: hidden; padding-bottom: .1em; margin-bottom: -.1em; }
.line-in { display: block; transform: translateY(112%); animation: up 1.1s cubic-bezier(.16,1,.3,1) forwards; }
@keyframes up { to { transform: none; } }

      Scroll progress helper

      const clamp = (n, a, b) => Math.min(b, Math.max(a, n));
const progress = (value, start, end) => clamp((value - start) / (end - start), 0, 1);

// example: fade out over the first 400px of scroll
el.style.opacity = 1 - progress(scrollY, 0, 400);

      Smooth anchor scrolling that respects a fixed header

      html { scroll-behavior: smooth; scroll-padding-top: 48px; }   /* height of your nav */
@media (prefers-reduced-motion: reduce) { html { scroll-behavior: auto; } }

      Reduced-motion safety net

      @media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
}

      Chapter 14

      Practice and where to go next

      Exercises, in order

      1. Change the feel. In your portfolio, set --ease to ease and the reveal duration to 300ms. Notice how much cheaper it feels, then put it back.
      2. Add a hover lift to the project tiles using the recipe in chapter 13.
      3. Add a new stagger. Make the tags at the bottom of each project appear one after another with --i.
      4. Build a scroll progress bar: a 3px line at the top of the page whose width equals scrollY / (document.height - window.height). Use the progress helper and write to the style directly.
      5. Make the stats count with a different easing. Try easeOutCubic, then compare.
      6. Add a "back to top" button that fades in after the user scrolls 600px (state plus a transition on opacity and visibility).
      7. Rebuild one effect without React. Make the scroll reveal work in a plain HTML file using only the vanilla code above.
      8. Try a scroll-driven animation with animation-timeline: view() inside an @supports block, in a browser that supports it.

      The habit that matters most

      When you see an animation you like on another site, open DevTools, inspect the element and read its CSS. Find the transition, the transform, the cubic-bezier. You now know what you are looking at. That is the fastest way to keep learning.
