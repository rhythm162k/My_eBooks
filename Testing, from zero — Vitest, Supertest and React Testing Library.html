      A practical guide

      Testing,
      from zero.

      How to test a Node, Express and PostgreSQL backend and a React frontend with Vitest, Supertest and Testing Library. Written for someone who has never written a test, using your own Movie Diary as the running example.

      Start here

      How to use this book

      Testing feels like a huge subject because it has a lot of vocabulary. The ideas underneath are small. This book gives you the vocabulary, then walks through every kind of test your project needs, in the order you should learn them.

      Read the chapters in order the first time. Each one builds on the last: you start with a test of one tiny function, then test an API route, then add a real database, then the React side. The demos let you break things on purpose and watch tests fail, which is the fastest way to understand why tests exist.

      Read this before running anything

      Never run tests against your real database. Tests create and delete data constantly. Your Supabase database that My Movie Diary uses in production must never be the one tests point at. Chapter 6 shows how to use a separate test database and how to add a guard that refuses to run otherwise.

      About the examples

      I haven't seen your code, so file names, table names and route paths here are typical: users and movies tables, /api/movies, /api/auth/login. Adapt the names to yours. The ideas stay the same. Where the right answer depends on how your project is built, the book says so.

      I also don't pin library versions. These tools change quickly, so when a command or option behaves differently on your machine, the official docs (vitest.dev, testing-library.com, playwright.dev) are the source of truth.

      Chapter 1

      What testing is, and the kinds of tests

      A test is a small program that runs your code and checks that it did what you expected. That's all.

      Without tests, you check your app by hand: start the server, open the browser, click around. That works until the app has fifty behaviors, and every change might break one of them. A test suite is a robot that does the clicking for you, in seconds, every time you change something.

      Every test has three parts

      This pattern is called Arrange, Act, Assert. Almost every test you will ever write follows it: 

      it('rejects a duplicate title', async () => {
  // ARRANGE: set up the situation
  const agent = await loginAs(app);
  await agent.post('/api/movies').send({ title: 'Inception' });

  // ACT: do the one thing you're testing
  const res = await agent.post('/api/movies').send({ title: 'inception' });

  // ASSERT: check the result
  expect(res.status).toBe(409);
});

      The test pyramid

      Tests come in different sizes. Small tests check one function and run in milliseconds. Big tests drive a real browser through your whole app and take seconds each. You want many small and fewer big, because small tests are fast and point at exactly what broke. Tap each layer:

      Live demo · the test pyramid

      Many modern teams, especially for web apps, lean toward the "testing trophy" shape: a lot of integration tests, since an API route talking to a real database is closer to how your app really works than a function tested alone. For your backend, that is where the most value is. A single Supertest test that sends a request through Express, runs the real SQL, and checks the response covers more risk than ten isolated function tests.

      Every kind of test, in one table

      Kind What it checks Typical tool
      Static analysis Typos, unused variables, type mistakes, before any code runs ESLint, TypeScript
      Unit One function or module in isolation Vitest
      Integration (API) Routes, middleware, auth and SQL working together Vitest + Supertest + test DB
      Component A React component: render it, click it, see the result Vitest + Testing Library
      End-to-end (E2E) A real browser using the real frontend and backend Playwright
      Smoke "Does the deployed app start and load at all?" A few quick checks Playwright or a script
      Regression "Did this old bug come back?" Not a tool, a habit: every fixed bug gets a test Any of the above
      Accessibility Labels, roles, contrast, keyboard use axe (vitest-axe, Playwright)
      Snapshot / visual Output or screenshots haven't changed unexpectedly Vitest snapshots, Playwright screenshots
      Contract Frontend and backend agree on the shape of requests and responses Shared schemas, Pact
      Performance / load Speed and behavior under many users autocannon, k6
      Security Auth rules, injection, dependency vulnerabilities Your own tests, npm audit
      Mutation "Would my tests notice if the code were wrong?" Advanced Stryker

      You don't need all of these. Chapters 2 to 9 cover the ones that matter most: unit, API integration, database, mocking, security and component tests. Chapter 10 covers the rest at a lighter level.

      What to test, and what not to

      • Test your own logic and the rules of your app: "duplicates return 409", "a user can only see their own movies", "no poster falls back to the placeholder".
      • Prioritize by risk: authentication, data ownership, validation and anything that would hurt if it silently broke.
      • Don't test the libraries. You don't need a test that Express can parse JSON or that bcrypt can hash. They have their own tests. Test that your code uses them correctly.
      • Test behavior, not implementation. "Posting a duplicate returns 409" survives a rewrite. "The function calls pool.query exactly once" breaks every time you refactor.

      Chapter 2

      Vitest from zero

      Vitest is the test runner: it finds your test files, runs them, and reports what passed and failed. Your frontend already uses Vite, which is why Vitest fits so well.

      Install and first run

      npm install -D vitest

      Add scripts to package.json:

      package.json 
      {
  "scripts": {
    "test": "vitest run",
    "test:watch": "vitest"
  }
}

      vitest run runs everything once and exits (good for CI). Plain vitest stays open in watch mode: it re-runs only the tests affected by the file you just saved. That instant feedback is the main reason people enjoy testing.

      Vitest treats any file ending in .test.js or .spec.js as a test file. Make your first one:

      src/utils/normalizeTitle.js 
      export function normalizeTitle(title) {
  return title.trim().toLowerCase();
}
      src/utils/normalizeTitle.test.js 
      import { describe, it, expect } from 'vitest';
import { normalizeTitle } from './normalizeTitle.js';

describe('normalizeTitle', () => {
  it('trims spaces and lowercases', () => {
    expect(normalizeTitle('  Inception ')).toBe('inception');
  });
});

      Run npm test. A green check means it passed. Now change the function to return title and run again: you get a red failure showing the expected value and the received value. A test you've never seen fail is a test you can't trust, so always see it fail once.

      The building blocks

      • describe('name', () => { ... }): groups related tests. Purely for organization.
      • it('does something', () => { ... }) (or test(...), identical): one test. Write the name as a sentence about behavior.
      • expect(value).matcher(expected): the assertion. If it's false, the test fails.

      Matchers you'll use constantly

      Matcher Use it for
      toBe(x) Exact equality for numbers, strings, booleans (===)
      toEqual(x) Deep equality for objects and arrays
      toMatchObject({...}) Object contains at least these fields (great for API responses with extra fields like ids)
      toContain(x) Array has an item, or string has a substring
      toHaveLength(n) Array or string length
      toBeTruthy() / toBeFalsy() Loose true/false checks
      toBeNull() / toBeUndefined() Exact null or undefined
      toThrow() A function throws an error
      toMatch(/regex/) A string matches a pattern
      not.toBe(x) Any matcher can be negated with .not
      resolves / rejects Promises: await expect(p).rejects.toThrow()

      Async tests

      Your backend is full of promises. Make the test function async and await things. Forgetting the await is the number one beginner bug: the test finishes before the assertion runs, and passes even if the code is broken. 

      it('loads a user', async () => {
  const user = await findUserByEmail('a@test.com');   // await!
  expect(user.email).toBe('a@test.com');
});

      Setup and cleanup hooks

      import { beforeAll, afterAll, beforeEach, afterEach } from 'vitest';

beforeAll(async () => { /* once, before all tests in this file  */ });
afterAll(async  () => { /* once, after all tests in this file   */ });
beforeEach(async () => { /* before every single test            */ });
afterEach(async  () => { /* after every single test             */ });

      You'll use beforeEach to reset the database (chapter 6) and afterAll to close connections.

      Testing many cases at once

      it.each([
  ['Inception',     'inception'],
  ['  Heat  ',      'heat'],
  ['THE MATRIX',    'the matrix'],
])('normalizes %j to %j', (input, expected) => {
  expect(normalizeTitle(input)).toBe(expected);
});

      Running only what you need

      • npx vitest run src/utils/normalizeTitle.test.js: one file.
      • npx vitest run -t "duplicate": tests whose name contains "duplicate".
      • it.only(...) runs just that test in the file; it.skip(...) skips one. Remove .only before committing, since it hides every other test.

      See red and green yourself

      This mini runner works like Vitest: it runs a list of tests against a function and reports each result. Pick an implementation of "is this title a duplicate?" and see which tests catch which bug.

      Live demo · a tiny test runner

        Notice how each bug is caught by a different test, and the failing test's name tells you exactly what's wrong. That is why test names should describe behavior.

        Chapter 3

        Unit tests: logic without I/O

        The easiest and fastest tests. A function takes input and returns output, with no database, no network, no server.

        Where unit tests fit in your backend

        Pull small decisions out of your route handlers into plain functions. A route handler that does everything (read the request, validate, query the DB, call OMDb, build the response) is hard to test in pieces. A route handler that calls small functions is easy.

        src/utils/movies.js 
        export const FALLBACK_POSTER = '/images/no-poster.png';

export function normalizeTitle(title) {
  return String(title ?? '').trim().toLowerCase();
}

export function validateMovieInput({ title }) {
  const errors = [];
  if (!title || !title.trim()) errors.push('Title is required');
  else if (title.length > 200) errors.push('Title is too long');
  return errors;                       // empty array means valid
}

export function pickPoster(omdbResponse) {
  const poster = omdbResponse?.Poster;
  return poster && poster !== 'N/A' ? poster : FALLBACK_POSTER;
}
        src/utils/movies.test.js 
        import { describe, it, expect } from 'vitest';
import { normalizeTitle, validateMovieInput, pickPoster, FALLBACK_POSTER } from './movies.js';

describe('validateMovieInput', () => {
  it('accepts a normal title', () => {
    expect(validateMovieInput({ title: 'Inception' })).toEqual([]);
  });
  it('rejects an empty title', () => {
    expect(validateMovieInput({ title: '' })).toContain('Title is required');
  });
  it('rejects a title made only of spaces', () => {
    expect(validateMovieInput({ title: '   ' })).toContain('Title is required');
  });
  it('rejects a title over 200 characters', () => {
    expect(validateMovieInput({ title: 'a'.repeat(201) })).toContain('Title is too long');
  });
});

describe('pickPoster', () => {
  it('uses the poster from OMDb when there is one', () => {
    expect(pickPoster({ Poster: 'https://img/x.jpg' })).toBe('https://img/x.jpg');
  });
  it('falls back when OMDb says N/A', () => {
    expect(pickPoster({ Poster: 'N/A' })).toBe(FALLBACK_POSTER);
  });
  it('falls back when OMDb returns nothing', () => {
    expect(pickPoster(undefined)).toBe(FALLBACK_POSTER);
  });
});

        Edge cases are where bugs live

        For every function, ask: what are the boundaries and the weird inputs?

        • Empty values ('', null, undefined, []).
        • The boundary itself (exactly 200 characters, then 201).
        • Surprising but valid input (leading spaces, unicode, very long strings).
        • The "nothing found" case (OMDb found no movie).

        The red, green, refactor loop (TDD)

        Test-driven development flips the order: write the test first, watch it fail (red), write just enough code to pass (green), then tidy up (refactor). You don't have to do this all the time. It's most useful when you are fixing a bug: write a test that reproduces the bug, watch it fail, fix the code, and the test now guards against that bug returning forever.

        What makes code easy to test

        Pure functions (same input, same output, no side effects) are the easiest. The more your logic is separated from I/O (database, network, clock), the less you need to set up. This is also just better design.

        Chapter 4

        Make the backend testable

        Before you can test your API, one structural change usually helps: separate "creating the app" from "starting the server".

        Split app.js and server.js

        If your file does app.listen(3000) at the bottom, importing it from a test starts a real server on a real port, and running tests in parallel causes "port already in use" errors. Supertest doesn't need a port. Give it the app object only.

        src/app.js: builds and exports the app. No listen. 
        import express from 'express';
import session from 'express-session';
import moviesRouter from './routes/movies.js';
import authRouter from './routes/auth.js';

const app = express();
app.use(express.json());
app.use(session({ /* store, secret, cookie options */ }));

app.use('/api/auth', authRouter);
app.use('/api/movies', moviesRouter);

export default app;
        src/server.js: the only place that starts listening 
        import app from './app.js';

const port = process.env.PORT || 3000;
app.listen(port, () => console.log(`Listening on ${port}`));

        Point npm start and npm run dev at server.js. Tests import app.js.

        Read configuration from environment variables

        Anything that should differ in tests (database URL, session secret, bcrypt cost) should come from process.env, not be hard-coded.

        src/db.js 
        import pg from 'pg';
export const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL });
        // wherever you hash passwords
const ROUNDS = Number(process.env.BCRYPT_ROUNDS ?? 15);
const hash = await bcrypt.hash(password, ROUNDS);
        Why bcrypt rounds matter for tests

        15 rounds is deliberately slow (around a second or more per hash), which is great for security and terrible for a test suite that creates dozens of users. In tests, set BCRYPT_ROUNDS=4 so hashing takes milliseconds. The code path is identical, so you still test the real behavior.

        A recommended folder layout

        backend/
├── src/
│   ├── app.js
│   ├── server.js
│   ├── db.js
│   ├── routes/            movies.js, auth.js
│   ├── services/          omdb.js
│   └── utils/             movies.js (+ movies.test.js beside it)
├── db/
│   └── schema.sql         tables: users, movies, session
├── tests/
│   ├── setup/             env.js, globalSetup.js
│   ├── helpers/           resetDb.js, loginAs.js
│   └── api/               movies.test.js, auth.test.js
├── .env.test              test database URL, test secrets
└── vitest.config.js

        Unit tests sit next to the file they test (movies.test.js). Heavier integration tests live in tests/api. Both are found automatically.

        The Vitest config for the backend

        vitest.config.js 
        import { defineConfig } from 'vitest/config';

export default defineConfig({
  test: {
    environment: 'node',
    setupFiles: ['./tests/setup/env.js'],            // runs before each test file
    globalSetup: ['./tests/setup/globalSetup.js'],   // runs once before everything
    fileParallelism: false,                          // test files share one database, run them one by one
    testTimeout: 10000,
  },
});
        tests/setup/env.js 
        import dotenv from 'dotenv';
dotenv.config({ path: '.env.test', override: true });
        .env.test (never commit real secrets) 
        DATABASE_URL=postgresql://postgres:postgres@localhost:5433/moviediary_test
SESSION_SECRET=test-secret
BCRYPT_ROUNDS=4
OMDB_API_KEY=test-key

        If your Vitest version doesn't recognize fileParallelism, check the Vitest docs for the current name of the option that runs test files one at a time.

        Chapter 5

        API tests with Supertest

        Supertest sends HTTP requests straight into your Express app and lets you assert on the response, without starting a server or opening a browser. 

        npm install -D supertest

        Your first API test

        tests/api/movies.test.js 
        import request from 'supertest';
import { describe, it, expect } from 'vitest';
import app from '../../src/app.js';

describe('GET /api/movies', () => {
  it('returns 401 when not signed in', async () => {
    const res = await request(app).get('/api/movies');

    expect(res.status).toBe(401);
  });
});

        The res object has res.status (number), res.body (parsed JSON), res.headers and res.text. You can also chain the check onto the request: await request(app).get('/api/movies').expect(401).

        Sending data and headers

        await request(app)
  .post('/api/movies')
  .send({ title: 'Inception' })        // JSON body (sets Content-Type for you)
  .set('Accept', 'application/json');  // any header

        Staying signed in: request.agent

        Your app uses session cookies. A plain request(app) call forgets cookies between requests, like opening a new incognito window each time. request.agent(app) remembers cookies like a real browser, so after logging in, later requests are authenticated.

        tests/helpers/loginAs.js (if you have an email and password login route) 
        import request from 'supertest';
import app from '../../src/app.js';

export async function loginAs(email = 'user@test.com', password = 'Passw0rd!') {
  await request(app).post('/api/auth/register').send({ email, password });

  const agent = request.agent(app);
  await agent.post('/api/auth/login').send({ email, password }).expect(200);
  return agent;                         // every call on this agent is signed in
}

        Auth when you only use Google sign-in

        Your tests can't click through Google's login page, and shouldn't try. You test your code, not Google's. Two common approaches:

        • Inject a fake user. Turn app.js into a factory, createApp({ testUser }), and when a testUser is passed, add a tiny middleware before your routes that sets req.user and req.isAuthenticated = () => true. Production never passes it. Tests do.
        • Test the OAuth callback logic separately as a unit: the function that finds or creates a user from a Google profile object can be tested by passing it a fake profile. 
        export function createApp({ testUser } = {}) {
  const app = express();
  app.use(express.json());
  app.use(session({ /* ... */ }));
  if (testUser) {
    app.use((req, res, next) => {
      req.user = testUser;
      req.isAuthenticated = () => true;
      next();
    });
  }
  app.use('/api/movies', moviesRouter);
  return app;
}
// in a test: const app = createApp({ testUser: { id: 1, email: 'a@test.com' } });

        What to check for each route

        For every endpoint, walk through the same short list. Each item is usually one test:

        1. Happy path: valid request, correct status and body.
        2. Not signed in: returns 401.
        3. Invalid input: empty, wrong type, too long, returns 400 with a useful message.
        4. Not found: an id that doesn't exist, returns 404.
        5. Ownership: user A cannot read, edit or delete user B's data.
        6. Business rules: duplicates return 409, and so on.

        Status codes cheat sheet

        Code Meaning When your API uses it
        200 OK Successful read or update
        201 Created A new movie was added
        204 No Content Deleted successfully, nothing to return
        400 Bad Request Invalid or missing input
        401 Unauthorized Not signed in
        403 Forbidden Signed in, but not allowed
        404 Not Found Doesn't exist (also a good reply for "belongs to someone else", so you don't reveal it exists)
        409 Conflict Duplicate entry
        500 Server Error A bug. Tests should rarely expect this on purpose

        A fuller test file

        tests/api/movies.test.js 
        import request from 'supertest';
import { describe, it, expect, beforeEach, afterAll } from 'vitest';
import app from '../../src/app.js';
import { pool } from '../../src/db.js';
import { resetDb } from '../helpers/resetDb.js';
import { loginAs } from '../helpers/loginAs.js';

beforeEach(resetDb);
afterAll(() => pool.end());

describe('POST /api/movies', () => {
  it('creates a movie and returns 201', async () => {
    const agent = await loginAs();

    const res = await agent.post('/api/movies').send({ title: 'Inception' });

    expect(res.status).toBe(201);
    expect(res.body).toMatchObject({ title: 'Inception' });
  });

  it('returns 400 when the title is missing', async () => {
    const agent = await loginAs();
    const res = await agent.post('/api/movies').send({});
    expect(res.status).toBe(400);
  });

  it('returns 409 for a duplicate title, ignoring case', async () => {
    const agent = await loginAs();
    await agent.post('/api/movies').send({ title: 'Inception' });

    const res = await agent.post('/api/movies').send({ title: 'inception' });

    expect(res.status).toBe(409);
  });

  it('returns 401 when not signed in', async () => {
    const res = await request(app).post('/api/movies').send({ title: 'Inception' });
    expect(res.status).toBe(401);
  });
});

describe('data ownership', () => {
  it("never shows one user's movies to another user", async () => {
    const alice = await loginAs('alice@test.com');
    const bob = await loginAs('bob@test.com');
    await alice.post('/api/movies').send({ title: 'Heat' });

    const res = await bob.get('/api/movies');

    expect(res.status).toBe(200);
    expect(res.body).toEqual([]);          // Bob sees nothing of Alice's
  });
});
        The cookie gotcha that confuses everyone

        If your session cookie is configured with secure: true, browsers only send it over HTTPS. Tests run over plain HTTP, so the agent will appear to log in but the next request is "not signed in". The usual fix is to set the flag from the environment, secure: process.env.NODE_ENV === 'production', and test the production flags separately (chapter 8). If your app sits behind a proxy in production, you'll also have app.set('trust proxy', 1), which is another thing to check when sessions misbehave.

        Chapter 6

        Testing with a real PostgreSQL database

        The part of your backend most likely to hide bugs is the SQL. To test it, you need a real database, a separate one, in a known state at the start of every test.

        Why a real database, not a fake

        You could mock pool.query and have it return fake rows, but then your tests only check that your code calls the database, not that your SQL is correct. A typo in a column name or a wrong WHERE user_id = $1 would pass. Real SQL against a real Postgres catches those. Postgres starts fast and test data is tiny, so this is cheap.

        Get a test database

        Pick one option. All of them give you a throwaway database named something with test in it.

        • Docker (recommended). One command, isolated, easy to delete:
        docker-compose.test.yml 
        services:
  db-test:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: postgres
      POSTGRES_DB: moviediary_test
    ports:
      - "5433:5432"
        docker compose -f docker-compose.test.yml up -d
        • Local Postgres (for example from Homebrew on your Mac): createdb moviediary_test, then use that in the URL.
        • A second, separate Supabase project only for tests. Works, but slower and needs internet.
        • In-process Postgres (PGlite): real Postgres compiled to WebAssembly, no install. Handy, but check that it supports everything you use before relying on it.

        Apply your schema once

        Keep your CREATE TABLE statements in a file (db/schema.sql) so you can build the test database from scratch. A global setup file runs once before all tests:

        tests/setup/globalSetup.js 
        import fs from 'node:fs';
import pg from 'pg';
import dotenv from 'dotenv';

export default async function setup() {
  dotenv.config({ path: '.env.test', override: true });
  const url = process.env.DATABASE_URL ?? '';

  // SAFETY GUARD: refuse to run against anything that isn't clearly a test database
  if (!/test/i.test(url)) {
    throw new Error('Refusing to run tests: DATABASE_URL does not look like a test database.');
  }

  const pool = new pg.Pool({ connectionString: url });
  await pool.query(fs.readFileSync('./db/schema.sql', 'utf8'));   // use IF NOT EXISTS in the file
  await pool.end();
}

        That guard is a seatbelt. If you ever misconfigure the URL, tests stop instead of wiping real data.

        Start every test from a clean slate

        tests/helpers/resetDb.js 
        import { pool } from '../../src/db.js';

export async function resetDb() {
  await pool.query('TRUNCATE users, movies, session RESTART IDENTITY CASCADE');
}

        TRUNCATE empties the tables, RESTART IDENTITY resets auto-increment ids to 1, and CASCADE also clears tables that reference them. Call it in beforeEach so no test inherits data from another. Adapt the table list to yours (the session table name depends on your session store).

        Why the clean slate matters

        Tests that share leftover data become order-dependent: they pass in one order and fail in another, or pass on your machine and fail in CI. Run this simulation of two tests sharing a database:

        Try it without cleanup: A then B fails. Switch the order to B then A and everything passes by luck. That is a flaky suite. Turn cleanup on and both orders pass.

        Helpers keep tests short

        If every test needs a user and some movies, don't repeat the setup. Write small helper functions (sometimes called factories):

        tests/helpers/factories.js 
        import { pool } from '../../src/db.js';

export async function createMovie(userId, title = 'Inception') {
  const { rows } = await pool.query(
    'INSERT INTO movies (user_id, title) VALUES ($1, $2) RETURNING *',
    [userId, title]
  );
  return rows[0];
}

        Tests can then check the database directly, which is useful to prove what really happened: 

        it('stores the movie for the signed-in user', async () => {
  const agent = await loginAs('a@test.com');
  await agent.post('/api/movies').send({ title: 'Inception' }).expect(201);

  const { rows } = await pool.query('SELECT title FROM movies');
  expect(rows).toHaveLength(1);
  expect(rows[0].title).toBe('Inception');
});

        Test that SQL injection fails

        You use parameterized queries. Prove they work by sending something nasty and checking that it's treated as plain text: 

        it('treats SQL in the title as plain text', async () => {
  const agent = await loginAs();
  const evil = "x'); DROP TABLE movies; --";

  await agent.post('/api/movies').send({ title: evil }).expect(201);

  const { rows } = await pool.query('SELECT title FROM movies');   // table still exists
  expect(rows[0].title).toBe(evil);                                // stored literally
});

        Close the connection when done

        An open pg pool keeps the Node process alive, so tests finish but the command hangs. Call await pool.end() in afterAll in files that use the database.

        Running test files in parallel

        Vitest runs test files in parallel by default. If they all share one database, one file's TRUNCATE deletes another file's data mid-test, producing random failures. That's why the config in chapter 4 runs files one at a time. When your suite grows large, a more advanced fix is one database (or schema) per worker.

        Chapter 7

        Mocks, spies and fake services

        Some things you don't want in a test: a real call to the OMDb API (slow, needs internet, has rate limits), a real email, or the real clock. You replace them with controlled stand-ins.

        The rule: mock at the edge of your system (third-party services, time, randomness). Don't mock your own database or your own code, or the test stops proving anything.

        The vocabulary

        • Mock / stub: a fake function that returns what you tell it.
        • Spy: a wrapper that records how a function was called, while still running it.
        • Fake timers: a clock you can move forward instantly.

        vi.fn: a fake function

        import { vi } from 'vitest';

const onSubmit = vi.fn();
onSubmit({ title: 'Inception' });

expect(onSubmit).toHaveBeenCalledTimes(1);
expect(onSubmit).toHaveBeenCalledWith({ title: 'Inception' });

const getPoster = vi.fn().mockResolvedValue('https://img/x.jpg');   // returns a promise

        vi.spyOn: watch a real function

        const spy = vi.spyOn(console, 'error').mockImplementation(() => {});   // silence noise
// ...run code that logs an error...
expect(spy).toHaveBeenCalled();
spy.mockRestore();

        Faking the OMDb call

        The quick way is to replace the global fetch for one test:

        src/services/omdb.test.js 
        import { describe, it, expect, vi, afterEach } from 'vitest';
import { getPoster } from './omdb.js';
import { FALLBACK_POSTER } from '../utils/movies.js';

afterEach(() => vi.unstubAllGlobals());

describe('getPoster', () => {
  it('returns the poster URL from OMDb', async () => {
    vi.stubGlobal('fetch', vi.fn().mockResolvedValue({
      ok: true,
      json: async () => ({ Response: 'True', Poster: 'https://img/inception.jpg' }),
    }));

    expect(await getPoster('Inception')).toBe('https://img/inception.jpg');
  });

  it('falls back when OMDb does not know the movie', async () => {
    vi.stubGlobal('fetch', vi.fn().mockResolvedValue({
      ok: true,
      json: async () => ({ Response: 'False', Error: 'Movie not found!' }),
    }));

    expect(await getPoster('asdkjhasd')).toBe(FALLBACK_POSTER);
  });

  it('falls back when the network fails', async () => {
    vi.stubGlobal('fetch', vi.fn().mockRejectedValue(new Error('offline')));

    expect(await getPoster('Inception')).toBe(FALLBACK_POSTER);
  });
});

        Notice the third test. Fake services let you simulate failures (offline, rate-limited, bad JSON) that are almost impossible to trigger on demand with the real API. Those failure paths are exactly where bugs hide.

        A better way: MSW (Mock Service Worker)

        Stubbing fetch by hand works but gets repetitive. MSW intercepts requests at the network level, so your code runs unchanged and you describe the fake server once. The same handlers work in backend tests and React tests. 

        npm install -D msw
        tests/mocks/server.js 
        import { setupServer } from 'msw/node';
import { http, HttpResponse } from 'msw';

export const server = setupServer(
  http.get('https://www.omdbapi.com/', ({ request }) => {
    const title = new URL(request.url).searchParams.get('t');
    if (title === 'Inception') {
      return HttpResponse.json({ Response: 'True', Poster: 'https://img/inception.jpg' });
    }
    return HttpResponse.json({ Response: 'False', Error: 'Movie not found!' });
  })
);
        in your test file or setup file 
        import { beforeAll, afterEach, afterAll } from 'vitest';
import { server } from '../mocks/server.js';

beforeAll(() => server.listen({
  // let Supertest's own requests to your app through; flag anything else unexpected
  onUnhandledRequest(req, print) {
    const host = new URL(req.url).hostname;
    if (host === '127.0.0.1' || host === 'localhost') return;
    print.error();
  },
}));
afterEach(() => server.resetHandlers());
afterAll(() => server.close());

        To simulate a failure in one test: server.use(http.get('https://www.omdbapi.com/', () => HttpResponse.error())). The override lasts until resetHandlers() runs after the test.

        Mocking whole modules

        vi.mock('./services/omdb.js') replaces an entire module with auto-mocked functions. It's powerful, but use it sparingly. It tests that your route calls a function, not that the whole chain works. Prefer MSW for network and keep module mocks for things you truly can't run.

        Faking time

        vi.useFakeTimers();
vi.setSystemTime(new Date('2026-01-01T00:00:00Z'));
// ...code that depends on "now"...
vi.advanceTimersByTime(60_000);     // jump a minute forward instantly
vi.useRealTimers();                 // always restore

        Chapter 8

        Testing security behavior

        Your resume lists bcrypt, secure cookies, OAuth, CORS and 401 handling. Tests are how you prove those claims are true and stay true.

        Authentication and authorization

        it.each([
  ['get',    '/api/movies'],
  ['post',   '/api/movies'],
  ['delete', '/api/movies/1'],
])('%s %s requires sign-in', async (method, path) => {
  const res = await request(app)[method](path);
  expect(res.status).toBe(401);
});

        This one it.each checks every protected route in a few lines. Add a route, add a row.

        Users can only touch their own data

        it("returns 404 when deleting another user's movie, and leaves it intact", async () => {
  const alice = await loginAs('alice@test.com');
  const bob = await loginAs('bob@test.com');
  const created = await alice.post('/api/movies').send({ title: 'Heat' });

  const res = await bob.delete(`/api/movies/${created.body.id}`);

  expect(res.status).toBe(404);                                  // or 403, whichever your API uses
  const { rows } = await pool.query('SELECT 1 FROM movies');
  expect(rows).toHaveLength(1);                                  // still there
});

        This is the single most valuable security test in a multi-user app. In a CRM, getting it wrong means one customer sees another's records.

        Passwords are hashed, never stored plain

        import bcrypt from 'bcrypt';

it('stores a bcrypt hash, not the password', async () => {
  await request(app).post('/api/auth/register').send({ email: 'a@test.com', password: 'Passw0rd!' });

  const { rows } = await pool.query('SELECT password_hash FROM users WHERE email = $1', ['a@test.com']);

  expect(rows[0].password_hash).not.toBe('Passw0rd!');
  expect(await bcrypt.compare('Passw0rd!', rows[0].password_hash)).toBe(true);
});

        Cookie flags

        it('sets an HttpOnly, SameSite session cookie', async () => {
  await request(app).post('/api/auth/register').send({ email: 'a@test.com', password: 'Passw0rd!' });
  const res = await request(app).post('/api/auth/login').send({ email: 'a@test.com', password: 'Passw0rd!' });

  const cookie = res.headers['set-cookie'].join(';');
  expect(cookie).toMatch(/HttpOnly/i);
  expect(cookie).toMatch(/SameSite=/i);
});

        The Secure flag normally only applies in production over HTTPS. To test it, run that single test with NODE_ENV=production behavior, or send the X-Forwarded-Proto: https header if your app trusts the proxy. Only add this if you can do it cleanly with your setup.

        Login failures

        • Wrong password returns 401 and does not reveal whether the email exists (same message for wrong email and wrong password).
        • Missing fields return 400.
        • The response body never includes password_hash. 
        expect(res.body).not.toHaveProperty('password_hash');

        Input validation and error handling

        • Send wrong types ({ title: 123 }, { title: null }, an array) and expect 400, not a crash.
        • Send malformed JSON and expect a clean 400.
        • On a server error, the response should not leak a stack trace or SQL text.

        CORS

        it('allows the real frontend origin', async () => {
  const res = await request(app).get('/api/health').set('Origin', 'https://my-diary.example.com');
  expect(res.headers['access-control-allow-origin']).toBe('https://my-diary.example.com');
});

it('does not allow a random origin', async () => {
  const res = await request(app).get('/api/health').set('Origin', 'https://evil.example.com');
  expect(res.headers['access-control-allow-origin']).toBeUndefined();
});

        Dependencies

        Run npm audit regularly. It's the cheapest security test there is, and you've already seen it in action on your Vite install.

        Chapter 9

        Testing React with Testing Library

        React Testing Library (RTL) renders your component in a fake browser and lets you interact with it the way a user would: find a button by its label, type, click, read the result.

        The guiding idea

        RTL's motto: the more your tests resemble how users use the software, the more confidence they give. A user doesn't know your state variable names. They see text, labels and buttons. So tests find things by what a user sees, not by CSS classes or component internals.

        Setup

        npm install -D @testing-library/react @testing-library/jest-dom @testing-library/user-event jsdom
        vite.config.js 
        import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  test: {
    environment: 'jsdom',                 // a simulated browser
    setupFiles: './src/test/setup.js',
    css: true,
  },
});
        src/test/setup.js 
        import '@testing-library/jest-dom/vitest';      // adds toBeInTheDocument(), toBeDisabled(), ...
import { afterEach } from 'vitest';
import { cleanup } from '@testing-library/react';

afterEach(() => cleanup());                      // unmount components between tests

        If your vite.config.js already has a defineConfig from vite, you may need import { defineConfig } from 'vitest/config' instead so TypeScript or your editor knows about the test key. Both work at runtime.

        A first component test

        src/components/MovieForm.test.jsx 
        import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { describe, it, expect, vi } from 'vitest';
import MovieForm from './MovieForm';

describe('MovieForm', () => {
  it('shows an error when the title is empty', async () => {
    const user = userEvent.setup();
    render(<MovieForm onSubmit={vi.fn()} />);

    await user.click(screen.getByRole('button', { name: /add movie/i }));

    expect(screen.getByText(/title is required/i)).toBeInTheDocument();
  });

  it('submits the typed title', async () => {
    const user = userEvent.setup();
    const onSubmit = vi.fn();
    render(<MovieForm onSubmit={onSubmit} />);

    await user.type(screen.getByLabelText(/title/i), 'Inception');
    await user.click(screen.getByRole('button', { name: /add movie/i }));

    expect(onSubmit).toHaveBeenCalledWith({ title: 'Inception' });
  });
});

        Arrange is render, act is user.type and user.click, assert is expect(...). Same pattern as everywhere.

        Finding things: the query families

        Query If found If missing Use for
        getBy... returns element throws Things that should be there now
        queryBy... returns element returns null Asserting something is not there
        findBy... returns element (waits) throws after timeout Things that appear later (after a fetch)

        Each family has variants. In order of preference (most user-like first):

        1. ByRole: getByRole('button', { name: /add movie/i }). Works like a screen reader. Best choice.
        2. ByLabelText: form fields by their label.
        3. ByPlaceholderText, ByText, ByDisplayValue.
        4. ByAltText, ByTitle.
        5. ByTestId: data-testid="...". A last resort for things with no accessible handle.

        Bonus: using roles and labels forces your UI to be accessible. If getByLabelText can't find your input, a real screen reader user couldn't either.

        userEvent over fireEvent

        user.click, user.type, user.keyboard simulate the full chain of real browser events (hover, focus, key presses). Always call userEvent.setup() first, and await every action.

        Components that load data

        Use MSW (chapter 7) so the component's real fetch runs against a fake API. This tests loading, success and error states.

        src/components/MovieList.test.jsx 
        import { render, screen } from '@testing-library/react';
import { http, HttpResponse } from 'msw';
import { server } from '../test/server';
import MovieList from './MovieList';

it('shows movies from the API', async () => {
  server.use(
    http.get('/api/movies', () => HttpResponse.json([{ id: 1, title: 'Inception' }]))
  );
  render(<MovieList />);

  expect(screen.getByText(/loading/i)).toBeInTheDocument();       // before the data arrives
  expect(await screen.findByText('Inception')).toBeInTheDocument(); // findBy waits for it
});

it('shows a message when the server fails', async () => {
  server.use(http.get('/api/movies', () => new HttpResponse(null, { status: 500 })));
  render(<MovieList />);

  expect(await screen.findByText(/something went wrong/i)).toBeInTheDocument();
});

it('asks the user to sign in on 401', async () => {
  server.use(http.get('/api/movies', () => new HttpResponse(null, { status: 401 })));
  render(<MovieList />);

  expect(await screen.findByText(/sign in/i)).toBeInTheDocument();
});

        In the frontend, relative URLs like /api/movies need a base in jsdom. If MSW complains, make your fetch calls use a configurable base URL (for example import.meta.env.VITE_API_URL) and use the full URL in the handler.

        Showing a 409 from the API

        it('shows a friendly message when the movie already exists', async () => {
  server.use(http.post('/api/movies', () =>
    HttpResponse.json({ error: 'Already in your diary' }, { status: 409 })));
  const user = userEvent.setup();
  render(<AddMovie />);

});

        Routers and context

        Components that use useNavigate, Link or a context need their provider around them in tests. Write one reusable helper:

        src/test/render.jsx 
        import { render } from '@testing-library/react';
import { MemoryRouter } from 'react-router-dom';
import { AuthProvider } from '../context/AuthContext';

export function renderApp(ui, { route = '/' } = {}) {
  return render(
    <MemoryRouter initialEntries={[route]}>
      <AuthProvider>{ui}</AuthProvider>
    </MemoryRouter>
  );
}

        Testing custom hooks

        import { renderHook, act } from '@testing-library/react';

it('increments', () => {
  const { result } = renderHook(() => useCounter());
  act(() => result.current.increment());
  expect(result.current.count).toBe(1);
});

        What not to test in React

        • Internal state values or which function got called internally. Test what the user sees.
        • Styling details (colors, exact CSS). Leave that to visual checks.
        • Third-party components. Trust them; test your use of them.
        • Large snapshots. They break on every tiny change and people stop reading them. Prefer explicit assertions.
        The "not wrapped in act(...)" warning

        This means something updated state after your test finished checking. Usually the fix is to await a user action or use findBy / waitFor for the thing that changes. Not to wrap everything in act yourself.

        Chapter 10

        End-to-end tests and every other kind

        Unit, API and component tests check pieces. End-to-end tests check that the pieces fit together, in a real browser.

        E2E with Playwright

        Playwright launches a real browser, visits your running app and clicks through it. It is slower and more fragile than the tests above, so write few, covering only the journeys that matter most: sign in, add a movie, see it in the list, delete it. 

        npm init playwright@latest
        playwright.config.js (key parts) 
        import { defineConfig } from '@playwright/test';

export default defineConfig({
  testDir: './e2e',
  use: { baseURL: 'http://localhost:5173', trace: 'on-first-retry' },
  webServer: [
    { command: 'npm run dev --prefix backend',  url: 'http://localhost:3000/api/health', reuseExistingServer: true },
    { command: 'npm run dev --prefix frontend', url: 'http://localhost:5173',            reuseExistingServer: true },
  ],
});
        e2e/add-movie.spec.js 
        import { test, expect } from '@playwright/test';

test('a user can add a movie and see it in the list', async ({ page }) => {
  await page.goto('/');
  await page.getByLabel('Email').fill('e2e@test.com');
  await page.getByLabel('Password').fill('Passw0rd!');
  await page.getByRole('button', { name: 'Sign in' }).click();

  await page.getByLabel('Title').fill('Inception');
  await page.getByRole('button', { name: /add movie/i }).click();

  await expect(page.getByText('Inception')).toBeVisible();
});

        Notice the queries are the same idea as Testing Library: find by role and label. Playwright auto-waits for elements, so you rarely need manual delays. E2E should run against the test database too (start the backend with .env.test), and the data should be reset before runs.

        A smoke test is a mini E2E: open the deployed site and check the homepage loads and the API health endpoint answers. Run it after each deploy.

        Code coverage

        npm install -D @vitest/coverage-v8
npx vitest run --coverage
        in the test config 
        coverage: {
  provider: 'v8',
  reporter: ['text', 'html'],      // open coverage/index.html for a line-by-line view
  include: ['src/**/*.js'],
},

        Coverage tells you which lines your tests executed. It is a map of what you haven't tested, which is useful. It does not tell you the tests are good: a test with no assertions still counts. Use it to find untested corners, not as a score. Chasing 100% leads to low-value tests. Something like 70 to 80% on backend logic, with the risky parts well covered, is a healthy target.

        Accessibility tests

        The axe engine finds common accessibility problems automatically. vitest-axe adds it to component tests, and Playwright has an axe package for whole pages. They catch missing labels, poor contrast and bad heading order, but not everything, so they complement manual keyboard checks.

        Snapshot and visual tests

        • Vitest snapshots (toMatchSnapshot(), toMatchInlineSnapshot()) record an output and fail if it changes. Good for small, stable outputs (a formatted error object), noisy for big UI trees.
        • Visual regression (Playwright's toHaveScreenshot()) compares screenshots pixel by pixel. Great for catching layout breaks on your portfolio-style pages, but screenshots differ across operating systems, so run them in one consistent environment such as CI.

        Contract testing

        When the frontend and backend are written separately, they can silently drift apart: the backend renames a field and the frontend breaks. A cheap defense is sharing the shape in one place (a schema library like Zod used by both) and testing responses against it. Heavier tools like Pact exist for large teams.

        Performance and load testing

        Your resume mentions a measured response time, and you can keep that honest with a tool. autocannon (Node) and k6 hammer an endpoint with many requests and report latency and errors. These aren't part of the regular test suite. You run them occasionally, against a test environment, never against production.

        Static checks, the cheapest tests

        ESLint catches whole classes of bugs (unused variables, missing awaits with the right rules) before code runs. TypeScript, if you ever adopt it, catches wrong types. They cost nothing per run and belong in CI beside the tests.

        Mutation testing (advanced)

        Stryker deliberately changes your code (flips a ===, deletes a line) and checks whether any test fails. If none do, your tests missed something. It's slow and mostly for mature projects. Worth knowing it exists.

        Chapter 13

        Writing tests that last, and fixing them when they break

        Habits of good tests

        • One behavior per test. When it fails, the name tells you what broke.
        • Name tests as sentences about behavior: returns 409 for a duplicate title, not test duplicate.
        • Independent tests. Any test should pass alone, in any order. (Chapter 6 demo.)
        • Fast. Slow suites don't get run. Keep bcrypt rounds low, avoid sleeps, and use beforeEach truncation instead of rebuilding the database.
        • Deterministic. No dependence on the real clock, network or random numbers. A test that sometimes fails is worse than no test.
        • Clear arrange step. Make it obvious what situation the test sets up. Use helpers, not copy-paste.
        • Watch it fail first at least once, so you know it can.
        • Every bug fixed gets a test that would have caught it.

        Common causes of flaky tests

        • Shared data between tests (no cleanup).
        • Test files running in parallel against one database.
        • Waiting a fixed time instead of waiting for a condition (findBy, waitFor).
        • Real network calls or the real clock.
        • A forgotten await.

        Debugging a failing test

        1. Read the diff. Vitest prints expected versus received. The answer is often right there.
        2. Print what you got: console.log(res.status, res.body) in API tests, screen.debug() in component tests (prints the rendered HTML).
        3. Narrow it down: it.only or vitest run -t "name".
        4. Use the UI: npm i -D @vitest/ui then npx vitest --ui gives a browser dashboard of your tests.
        5. Check the database directly with psql or a client against the test DB to see what's really stored.
        6. Ask: is the code wrong, or is the test wrong? Both happen.

        Common errors and fixes

        You see Likely cause Fix
        Tests pass but the command never exits An open DB pool or server await pool.end() in afterAll; don't call listen in app.js
        EADDRINUSE The app starts a real server on import Split app.js and server.js
        relation "movies" does not exist Schema not applied to the test DB Check globalSetup and the URL
        ECONNREFUSED to port 5433 The test database isn't running docker compose ... up -d
        Logged in, but next request is 401 Using request(app) instead of an agent, or a secure cookie over HTTP Use request.agent(app); make secure depend on NODE_ENV
        Test passes even when code is broken Missing await or no assertion Add await; consider expect.assertions(n)
        Tests time out Slow bcrypt, hung promise, or waiting for something that never happens Lower BCRYPT_ROUNDS; check mocks resolve
        toBeInTheDocument is not a function jest-dom isn't registered Import @testing-library/jest-dom/vitest in the setup file
        document is not defined Frontend tests are running in the Node environment Set environment: 'jsdom'
        Unable to find an element It isn't rendered yet, or the query is wrong Use findBy for async; print with screen.debug()
        Random failures that disappear on re-run Shared state or parallel files Reset data in beforeEach; run files serially
        MSW reports requests to 127.0.0.1 Supertest's own calls reach MSW Ignore localhost in onUnhandledRequest

        Practice and where to go next

        Exercises, in order

        1. Break and fix. Write the normalizeTitle test, watch it fail by breaking the function, then fix it.
        2. Test every util in your backend with at least one edge case each.
        3. Split app.js and server.js and write the "401 when not signed in" test for each route using it.each.
        4. Build the test database with Docker, the safety guard and resetDb.
        5. Write the duplicate test (409), then the case-insensitive version.
        6. Write the ownership test with two users. Temporarily remove the user_id filter from your SQL and watch it fail. Put it back.
        7. Mock OMDb with MSW: success, not found, network error.
        8. Test your form component and the 409 message on the frontend.
        9. Add the GitHub Actions workflow and get a green check.
        10. Add one Playwright journey and one accessibility check.

        The one habit that matters most

        The next time you fix a bug, write the failing test first. Within a month, you'll have a suite that protects you from your own past mistakes, and you'll start to feel uncomfortable changing code without one.
